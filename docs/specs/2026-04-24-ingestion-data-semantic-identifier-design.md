# Ingestion Data Semantic Identifier Design

**Date:** 2026-04-24

## Goal

Refactor `ingestion_data` access so module screens do not depend only on autogenerated `metric_key` values. Add a reusable semantic identifier, expose it through the API/runtime, and provide a shared frontend lookup helper with semantic-first fallback behavior.

## Current Problems

- Many rows use autogenerated `metric_key` values such as `taxes_modules_taxes_views_index_075`.
- The same business metric can appear in multiple rows with different `metric_key` values.
- `label` is unreliable for lookup because some rows store the display value instead of a human-readable metric name.
- Frontend code currently resolves metrics by exact `metric_key`, which makes screens fragile when extraction order or generated keys change.

## Decisions

### 1. Additive Schema Change

Add a new nullable `semantic_identifier text` column to `public.ingestion_data`.

Rules:

- `semantic_identifier` is reusable across multiple rows when they represent the same business metric.
- `semantic_identifier` is optional so legacy/generated rows can continue to exist during migration.
- `metric_key` remains unique and remains the backward-compatible row key.
- `label` remains human-readable metadata, but it is no longer treated as the primary identifier.

Database updates:

- Add `semantic_identifier text` to:
  - `supabase/schema.sql`
  - `supabase/setup.sql`
- Add a non-unique index on `semantic_identifier`.
- Add `semantic_identifier` to:
  - `supabase/ingestion_data.csv`
  - `supabase/seed_ingestion_data.sql`
- Update seed upserts so `semantic_identifier = excluded.semantic_identifier`.

## Data Population Strategy

### Curated Metrics

Explicitly set `semantic_identifier` for curated/manual metrics first:

- Mortgage overlay metrics such as `mortgage.total_due`
- GP summary metrics such as `gp.total_gp_sponsors`
- Insurance overview and trend metrics where the business meaning is known
- Taxes metrics where business meaning is clear and stable

### Generated HTML Metrics

Do not force all autogenerated HTML-extracted rows to receive semantic identifiers immediately.

Rules:

- Keep existing autogenerated `metric_key` generation unchanged for now.
- Allow extracted rows to keep `semantic_identifier = null` unless there is a reliable curated mapping.
- This avoids inventing unstable semantic names from weak text context.

## API And Runtime Contract

Expose `semantic_identifier` everywhere that metric rows are read or cached.

Update:

- `api/_lib/metrics.js`
- `api/metrics.js`
- `assets/js/supabase-data.js`

Changes:

- Include `semantic_identifier` in every `select` list.
- Preserve existing `metric_key` query behavior for backward compatibility.
- Keep `getRow(metricKey)` working exactly as it does now.

## Shared Frontend Lookup Helper

Add shared lookup helpers in `assets/js/supabase-data.js`.

Public helper:

```js
getMetricValue(data, {
  key,
  metricKey,
  label,
  fallbackMetricKeys = [],
  defaultValue = null,
  preferNumeric = false,
})
```

Supporting helper:

```js
getMetricRow(data, {
  key,
  metricKey,
  label,
  fallbackMetricKeys = [],
})
```

### Lookup Priority

Resolve rows in this order:

1. Match `semantic_identifier` from `key` or `metricKey`
2. Fallback to normalized `label`
3. Fallback to exact legacy `metric_key` from `metricKey`
4. Fallback to exact legacy keys from `fallbackMetricKeys`

### Return Behavior

- `getMetricValue(...)` returns `value_display` by default.
- `getMetricValue(...)` returns `value_numeric` when `preferNumeric: true`.
- If no match exists, return `defaultValue`.
- `getMetricRow(...)` returns the full matched row or `null`.

### Label Normalization

Normalize labels by:

- coercing to string
- trimming
- lowercasing
- collapsing repeated whitespace
- removing lightweight punctuation noise

This should allow matches such as:

- `Total Tax Liability`
- ` total tax liability `
- `Total Tax Liability:`

### Duplicate Semantic Identifier Handling

If multiple rows share the same `semantic_identifier`:

- keep dataset order stable
- return the first row with a usable value
- do not throw an error

This preserves deterministic behavior while allowing intentional duplicates during migration.

## Runtime Indexing

Enhance `assets/js/supabase-data.js` caching so rows can be resolved by:

- `metric_key`
- normalized `label`
- `semantic_identifier`

Suggested internal runtime state:

- `rowsByKey`
- `rowsBySemanticIdentifier`
- `rowsByNormalizedLabel`

For `rowsBySemanticIdentifier` and `rowsByNormalizedLabel`, store arrays in fetch order rather than a single row so the helper can apply consistent first-match logic.

## Screen Migration Plan

### Mortgage

Update `modules/mortgage/views/current-debt-supabase.js` to prefer semantic identifiers instead of hardcoded legacy keys.

Examples:

- `principal-balance` -> `mortgage.principal_balance`
- `interest-rate` -> `mortgage.interest_rate`
- `total-due` -> `mortgage.total_due`

Keep the old legacy `metric_key` strings as fallback values during migration.

### Insurance

Update the insurance page script to use the shared helper for:

- overview cards
- trend bars
- trend table

Each trend entry should carry:

- `key` for the new `semantic_identifier`
- `fallbackMetricKeys` for the existing generated `metric_key`

### Taxes

Keep existing `data-metric-key` bindings working.

For now:

- do not rewrite all annotated spans
- add semantic identifiers in curated seed rows where the meaning is reliable
- use shared helper logic first in any scripted or especially fragile lookup paths

This avoids a risky full-page rewrite while still enabling semantic migration.

### GP

Migrate curated summary metrics immediately because they already have stable business meaning.

Examples:

- `gp.total_gp_sponsors`
- `gp.k1_partners_in_manager_entity`
- `gp.source_k1_year`

## Backward Compatibility

The refactor must not break existing module screens.

Compatibility rules:

- existing `data-metric-key` DOM updates continue to work
- existing `getRow(metricKey)` calls continue to work
- legacy rows without `semantic_identifier` remain readable
- screens can adopt semantic lookup incrementally

## Error Handling

If no semantic match exists:

- fallback to normalized label
- then fallback to legacy keys
- then return the caller-provided default value

If a matched row has an unusable display value:

- `getMetricValue(..., { preferNumeric: false })` should continue fallback resolution until it finds a usable display value or exhausts candidates

If a matched row has an unusable numeric value:

- `getMetricValue(..., { preferNumeric: true })` should continue fallback resolution until it finds a finite numeric value or exhausts candidates

## Testing Plan

### Runtime Tests

Add tests for:

- semantic identifier match wins over label and metric key
- normalized label match works when semantic identifier is absent
- legacy `metric_key` fallback still works
- `fallbackMetricKeys` are honored
- `preferNumeric` returns `value_numeric`
- duplicate semantic identifiers resolve deterministically
- missing rows return `defaultValue`

### API Tests

Add tests to confirm:

- `semantic_identifier` is included in API select fields
- metric fetch responses include `semantic_identifier`
- existing key-based query behavior is unchanged

### Seed And Extraction Tests

Add tests to confirm:

- curated manual metrics include `semantic_identifier`
- CSV and SQL seed outputs include the new column
- upserts preserve `semantic_identifier`

### Module Tests

Update module-focused tests for at least:

- mortgage semantic-first overlay lookup
- insurance trend lookup using semantic key plus legacy fallback
- GP summary metrics using semantic identifiers

## Non-Goals

- Rebuilding the frontend in a framework
- Replacing `metric_key` as the database row key
- Assigning semantic identifiers to every extracted HTML metric in one pass
- Renaming or repairing every existing `label` value immediately

## Recommended Implementation Order

1. Add `semantic_identifier` to schema, setup, seed CSV, and seed SQL.
2. Update seed generation for curated metrics.
3. Update API select fields and runtime row caching.
4. Add shared `getMetricRow(...)` and `getMetricValue(...)` helpers.
5. Migrate GP, mortgage, and insurance scripted lookups to semantic-first resolution with legacy fallbacks.
6. Add and update automated tests.

## Success Criteria

This work is complete when:

- `ingestion_data` supports reusable `semantic_identifier` values
- the API and runtime expose `semantic_identifier`
- the shared frontend helper resolves metrics by semantic identifier, then label, then legacy key
- migrated screens no longer depend only on autogenerated `metric_key` values
- legacy screens continue to render without regression
- automated tests cover the new resolution order
